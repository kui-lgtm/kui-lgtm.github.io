01 / Game loop

한 프레임의 실행 순서

메인 루프는 지면에서만 점프를 허용하고, 속도와 위치를 매 프레임 갱신한 뒤 충돌을 검사합니다. 장애물이 화면을 벗어나면 무작위 간격으로 다시 배치하고 점수를 1 올립니다.

  1. 입력 읽기PA0 점프와 PA1 정지 버튼을 내부 풀업 입력으로 읽습니다.
  2. 점프 물리초기 속도 10을 부여하고 매 프레임 2씩 감소시켜 상승과 낙하를 만듭니다.
  3. 장애물 이동obstacle_x -= 3으로 이동하며, 화면 밖에서는 132 + rand()%100 위치로 복귀합니다.
  4. 충돌 판정X 구간이 겹치고 공룡 높이가 8보다 낮으면 게임오버 상태로 전환합니다.
  5. 프레임 출력8개 OLED 페이지를 순회해 지면·공룡·선인장을 OR 합성한 뒤 컬럼별로 전송합니다.
player_y += player_vel;
if (player_y > 0) player_vel -= 2;
else { player_y = 0; player_vel = 0; }

obstacle_x -= 3;
if (obstacle_x < 17 && obstacle_x + 5 > 10)
  if (player_y < 8) GameOver();
02 / Pin sharing

한정된 GPIO를 안전하게 공유

PB6는 SPI MOSI와 LCD RS가 함께 사용하고, PB0–PB2는 LCD 데이터와 상태 LED가 공유합니다. 따라서 데이터 값보다 “어느 장치가 현재 신호를 받아도 되는가”를 먼저 제어했습니다.

Shared pinsRole ARole BProtection rule
PB6SPI MOSILCD RSSPI 동안 LCD EN을 Low로 유지하고 전송 후 MOSI를 Low로 복원
PB0–PB2LCD D4–D6Red·Green·White LEDLCD EN 펄스가 끝난 직후 저장해 둔 LED 하위 니블을 복원
SPI busSH1106MAX7219각 장치의 CS를 독립 제어하고 LCD 쓰기 중에는 두 CS를 모두 High로 유지
초기화 순서: CS High와 LCD EN Low를 먼저 보장한 뒤 LCD → OLED → MAX7219 순으로 초기화했습니다. 전원 인가 직후 핀 흔들림이 명령으로 해석되는 상황을 줄이기 위한 순서입니다.
03 / State & limits

상태 피드백과 다음 개선점

게임 상태를 화면 하나에만 의존하지 않고 LED와 LCD, 7-segment에 나누어 표시했습니다. 사용자는 출력 장치만 보고도 실행·점프·정지·게임오버 상태를 구분할 수 있습니다.

  • 진행: Green LED ON, LCD에 최고 점수, 7-segment에 현재 점수 표시
  • 점프: 공중에 있는 동안 White LED ON
  • 정지: 50 ms 디바운스 후 이동과 렌더링을 멈추고 LCD에 STOP 표시
  • 게임오버: Red LED ON, 점수 표시를 5회 점멸하고 점프 버튼으로 재시작
  • 개선 방향: _delay_ms() 기반 루프를 타이머 인터럽트 기반 고정 프레임으로 바꾸고, 큰 스프라이트가 페이지 경계를 넘을 때의 합성 로직을 일반화
01 / Overview

게임 로직과 장치 제어를 하나의 흐름으로

구성

점프·정지 버튼의 입력을 읽고, SH1106 OLED에는 캐릭터와 장애물을, MAX7219에는 점수를, 문자 LCD와 LED에는 게임 상태를 표시하도록 구성했습니다.

핵심 과제

제한된 핀 때문에 LCD의 RS 핀과 SPI의 MOSI 핀을 공유해야 했습니다. 통신 순서가 어긋나면 LCD가 SPI 데이터를 명령으로 해석할 수 있어 장치 간 간섭을 막는 제어가 필요했습니다.

해결

SPI 전송 중 LCD의 Enable을 Low로 유지하고, LCD를 제어할 때는 OLED와 MAX7219의 Chip Select를 비활성화했습니다. 각 전송 직후 핀 상태를 복원해 공유 핀에서도 출력이 안정적으로 이어지도록 했습니다.

배운 점

기능을 추가하는 것만큼 주변장치의 활성 조건과 버스 점유 시점을 명확하게 정의하는 일이 중요했습니다. 핀맵과 상태 전환을 코드 구조에 반영하는 방법을 익혔습니다.
