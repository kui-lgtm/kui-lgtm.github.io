Parallelism / Integrity

빠르게 처리하고, 같은 결과를 보장하기

worker 확장에 따른 성능 변화와 동기화 해제 시 발생하는 오류를 함께 비교해 처리량과 정확성 사이의 경계를 확인했습니다.

01 / Scaling

worker를 늘리면 빨라지지만 선형으로 늘지는 않는다

1,000개 메일을 chunk 1로 처리했을 때 process 8개는 22.477초, thread 8개는 22.552초를 기록했습니다. 두 방식은 거의 같은 성능을 보였지만 8배가 아닌 약 5.6배에서 포화됐습니다.

  • CPU 경쟁: BERT feature extraction이 모든 core와 cache를 강하게 사용
  • Memory pressure: 여러 worker가 동시에 모델 데이터를 읽으며 대역폭 경쟁
  • Synchronization: index 예약과 통계 병합을 위한 짧은 critical section 발생
02 / Race condition

더 빨라 보이는 실행이 정답을 깨뜨렸다

8 process × 1 BERT thread 조건에서 race delay 1,000μs를 넣자, synchronization on은 정확히 200개를 처리했지만 off는 239개를 처리했습니다. 같은 index와 count를 여러 process가 동시에 읽은 결과입니다.

판단: lock overhead가 작아도 작업 예약, accepted count, 통계 병합은 반드시 원자적으로 보호해야 합니다.
03 / Hybrid design

process와 thread의 역할을 작업 성격에 맞춰 분리

parent는 파일 목록과 공유 index를 준비하고 child process는 I/O·count·SVM을 담당합니다. 각 process 안의 pthread는 BERT embedding에만 집중하며 mutex와 condition variable을 통해 job과 feature를 전달합니다.

  1. Parent파일 목록, SVM 모델, shared global index 준비
  2. Child process파일 예약, 읽기, 처리 개수 제한, SVM 예측
  3. BERT thread메일 버퍼를 384차원 feature로 변환
  4. Protected mergemutex로 전역 통계를 일관되게 합산
Engineering deep dive

병목을 측정한 뒤 병렬화 구조를 선택

process가 무겁고 thread가 가볍다는 일반론 대신, 실제 단계별 시간과 메모리 동작을 기준으로 구조를 비교했습니다.

01 / Baseline

전체 시간의 96.34%가 BERT embedding

single process가 메일을 순차적으로 읽고 384차원 embedding을 만든 뒤 SVM으로 분류했습니다. 3,000개 메일 기준 99.136초 중 embedding이 95.508초를 차지해, I/O가 아니라 CPU 연산을 병렬화해야 한다는 결론을 얻었습니다.

02 / Structure comparison

pipeline보다 work sharing이 더 적합했다

단일 worker 비교에서는 thread-workshare가 67.883초로 가장 빨랐고 process-workshare가 67.994초로 뒤를 이었습니다. 중간 feature를 queue로 넘기는 pipeline보다 worker가 파일 하나의 전체 분류를 끝내는 방식이 동기화와 전달 비용을 줄였습니다.

03 / Hybrid

총 BERT worker가 같아도 배치가 성능을 바꾼다

총 8개의 BERT worker를 유지한 채 process와 thread 조합을 바꿨습니다. 8 process × 1 thread는 22.906초였지만 1 process × 8 threads는 132.613초였습니다. queue capacity 1에서 단일 process가 I/O와 SVM을 맡으면 handoff가 직렬화되기 때문입니다.

04 / Synchronization

보호해야 할 데이터의 경계를 명확히

동기화 대상을 global index, accepted count, stats, BERT job/result queue, start barrier로 나눴습니다. queue는 mutex와 condition variable로 보호하고, process-shared 데이터는 별도 mutex 안에서 검사와 갱신이 함께 일어나도록 했습니다.

lock(global_mutex)
  reserve next_index
  check_and_increment accepted_emails
unlock(global_mutex)

lock(stats_mutex)
  merge local_stats into global_stats
unlock(stats_mutex)
실험 해석: mutex·spinlock·adaptive mutex·POSIX semaphore의 실행 차이는 1% 미만이었습니다. 이 workload에서는 lock 종류보다 critical section의 정확한 범위가 더 중요했습니다.
03 / Retrospective

가벼운 thread가 항상 빠르지는 않았다

담당 범위

5인 팀에서 Thread & Synchronization 파트를 맡아 thread 기반 병렬화 모델을 구현하고 mutex·spinlock 등 동기화 도구를 비교했습니다. 공식 역할 기여도는 20%였습니다.

핵심 발견

read-only BERT 모델은 fork 이후 Copy-on-Write로 효율적으로 공유됐고, thread 방식은 context migration과 모델 인스턴스 복제의 영향을 받았습니다. 실제 workload에서는 process가 thread와 같거나 조금 더 빨랐습니다.
